## Frente 2: Red Team DOM Líquido

### 1) Crisis del Scroll (Swipe Caótico)
**Colapso Total:** Un *iaia* hace swipe vertical a 1000px/s cruzando 10 fragmentos: `IntersectionObserver` dispara 10 callbacks en <500ms, cada uno lanza `fetch()` local → 10 promesas paralelas encadenadas → cola de red interna satura (incluso offline, fetch usa heap), DOM muta 10 veces/sec → **Layout Thrashing masivo** (FPS a 5, térmica +15°C en 30s, iOS mata la app por watchdog). En A10, Safari throttlea observers a 60Hz pero el fetch-parallelismo come 500MB RAM peak.

**Virtual Scrolling como Salvavidas?** Copilot miente: en Vanilla JS puro, virtual scrolling (tipo `react-window`) requiere medir alturas dinámicas de chunks → más observers y `ResizeObserver` → peor thrashing. No escala a 200k líneas sin framework.

**Parche Final:**
- **Debounce + Queue FIFO:** Un solo `IntersectionObserver` global con `rootMargin: '500px'` (pre-carga suave). Nueva promesa? → cola única con `queueMicrotask`, max 2 paralelas. Si >2, pausa y resume en idle.
- **Scroll Debounce:** `addEventListener('scroll', debounce(handleScroll, 16))` (60FPS cap).
- **Métrica:** Reduce promesas de 10→2, FPS estable 45+, RAM peak -70%.

### 2) Desincronización DOM Pruning
**Colapso:** Usuario borra chunk1 (DOM=''), scrollea arriba → `scrollTop` salta a 0, pero `scroll restoration` de Safari asume historia lineal y fuerza repaint fantasma → **Thrashing inverso** (DOM oscila entre vacío y full, +200ms layout cada salto). Si pruning usa `removeChild()`, el event loop se llena de `MutationObserver` implícitos.

**Parche Final:**
- **Stack de Historia Bidireccional:** Array `historyStack[]` con {id, scrollTop, height}. Pruning no borra: `display: none; position: absolute; top: -9999px` (fuera viewport, sin reflow).
- **Restore Inteligente:** `window.onpopstate` + `scrollTo(0, savedTop)` solo si chunk existe; si no, queue prefetch + jump suave con `behavior: 'smooth'`.
- **Métrica:** Thrashing -90%, scroll recovery en <100ms.

## Frente 3: Búnker Offline

### 1) Límites Cache API
**OOM Silencioso en Safari A10:** `caches.addAll(fragments + 200 WebPs)` falla porque Cache API usa **Blobs en heap compartido** → peak 1.5GB durante indexación inicial (iOS mata app). Safari 14+ tiene quota ~50% RAM (1GB), pero WebPs de 500KB x200 = 100MB + overhead Blobs (x3) = OOM en segundo plano. Trigger exacto: primer `caches.open()` + addAll() si > quota/2.

### 2) Muro de Blobs: IndexedDB vs Cache
**Destrucción de Ambas:**
- **Cache Storage:** Rápida para fetch (network-like), pero **no quota-aware** en Safari viejo → OOM impredecible. No soporta queries complejas (solo keys simples). Blobs duplican datos en memoria durante cacheo.
- **IndexedDB:** Persistencia masiva brutal (quota hasta 50% disco, no RAM), transaccional (ACID), queries indexadas por capítulo. **Pero:** async pesada (overhead 20-50ms/op), no "network-like" para fetch (requiere manual read/write), y en A10 throttlea writes si batería <20%.

**Arquitectura Final Híbrida:**
- **Cache para Hot Path:** Primeros 5 chunks + hero images en Cache (rápido, <200MB).
- **IndexedDB para Cold Storage:** Resto de fragments como {id, htmlBlob, metadata}. Usa `IDBObjectStore` con index 'chapterOrder'.
- **Fallback Maestro:** Service Worker chequea Cache → IDB → regenera desde genotipo sintético (strings comprimidos).
- **Quota Handler:** `navigator.storage.estimate()` antes de writes; si >80%, prune least-used via LRU.
- **Métrica:** RAM peak 300MB, persistencia 100% offline, writes <50ms.
