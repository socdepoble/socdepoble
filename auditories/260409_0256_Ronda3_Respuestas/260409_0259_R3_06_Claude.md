## FRENTE 2: RED TEAM — Destruyendo el DOM Líquido

### Crisis del Scroll en iPad A10

El IntersectionObserver con `rootMargin: '800px'` dispara `loadNextChunk()` cada vez que el sentinel entra en la zona de precarga. Si la usuaria hace swipe rápido atravesando 10 fragmentos en un segundo, el resultado es:

- 10 llamadas a `fetch()` se encolan simultáneamente
- iOS Safari limita conexiones simultáneas al mismo origen a 6; las restantes esperan
- Cada `fetch` resuelve y ejecuta `createContextualFragment()` + `insertBefore()` en el main thread, uno tras otro
- Con fragmentos de ~20 artículos cada uno, el DOM crece de golpe en cientos de nodos mientras el motor de layout intenta mantener la posición de scroll
- El resultado probable en A10 con 2GB: jank severo o kill del proceso WebView por presión de memoria

**Solución — cola serializada con concurrencia máxima 1:**

```javascript
class ChunkQueue {
  #queue = [];
  #loading = false;
  #abortController = null;

  enqueue(chunkEntry) {
    // Si ya está en cola o cargado, ignorar
    if (this.#queue.includes(chunkEntry) || loadedChunks.has(chunkEntry.chunk)) return;
    this.#queue.push(chunkEntry);
    this.#drain();
  }

  cancel() {
    // Cancelar fetch en curso si el usuario cambia de dirección
    this.#abortController?.abort();
    this.#queue = [];
    this.#loading = false;
  }

  async #drain() {
    if (this.#loading || this.#queue.length === 0) return;
    this.#loading = true;
    const entry = this.#queue.shift();
    
    this.#abortController = new AbortController();
    try {
      const html = await fetch(`./chunks/${entry.chunk}`, {
        signal: this.#abortController.signal
      }).then(r => r.text());
      
      injectChunk(html, entry);
    } catch (e) {
      if (e.name !== 'AbortError') console.error('Chunk load failed:', e);
    } finally {
      this.#loading = false;
      this.#drain(); // siguiente en cola
    }
  }
}
```

**Sobre Virtual Scrolling:** Es la solución correcta a largo plazo pero tiene un coste de implementación alto en Vanilla JS puro. El problema específico de Sóc de Poble es que los artículos tienen alturas muy variables (algunos son 200px, otros 4000px con imágenes), lo que hace inestable cualquier cálculo de posición basado en alturas estimadas. Si queréis virtual scrolling real, la única opción pragmática es usar una librería probada como `@tanstack/virtual` o `lit-virtualizer` — implementarlo desde cero para alturas dinámicas es una trampa de complejidad que os va a consumir semanas.

### Desincronización del DOM Pruning y Scroll Restoration

El DOM Pruning (eliminar fragmentos superiores ya leídos) es donde el sistema puede colapsar de forma silenciosa y catastrófica.

**El problema exacto:**

Cuando elimináis un nodo del DOM, el navegador recalcula la posición de todo lo que viene después. Si el nodo eliminado tenía altura H, el `scrollY` del usuario se desplaza -H en el mismo frame. El resultado visible: el contenido salta hacia arriba, la usuaria percibe un teleport de pantalla. En iOS esto es especialmente agresivo porque el momentum scroll continúa después del gesto.

**La solución es anclar el scroll antes de mutar el DOM:**

```javascript
function pruneTopChunk(nodeToRemove) {
  // 1. Medir altura del nodo ANTES de eliminarlo
  const removedHeight = nodeToRemove.getBoundingClientRect().height;
  
  // 2. Guardar scrollY actual
  const scrollBefore = window.scrollY;
  
  // 3. Eliminar el nodo
  nodeToRemove.remove();
  
  // 4. Compensar inmediatamente el scroll
  // (debe ser síncrono, en el mismo task, sin awaits)
  window.scrollTo({ top: scrollBefore - removedHeight, behavior: 'instant' });
  
  // 5. Registrar que este chunk está "purgado" pero disponible
  prunedChunks.add(nodeToRemove.dataset.chunkId);
}
```

**El problema del scroll hacia arriba tras pruning:**

Si el usuario hace scroll hacia arriba hacia un chunk purgado, necesitáis reinjectarlo y reposicionar el scroll. Esto requiere conocer la altura que tenía el chunk antes de eliminarlo — que ya no existe en el DOM.

La solución es un **placeholder con altura reservada**:

```javascript
function pruneTopChunk(node) {
  const height = node.getBoundingClientRect().height;
  
  // Sustituir por placeholder invisible que mantiene la altura
  const placeholder = document.createElement('div');
  placeholder.dataset.chunkPlaceholder = node.dataset.chunkId;
  placeholder.style.height = `${height}px`;
  placeholder.style.contain = 'strict'; // evita que participe en layout flow
  
  node.replaceWith(placeholder);
  
  // Observar el placeholder para reinyectar si el usuario sube
  reverseObserver.observe(placeholder);
}
```

## FRENTE 3: BÚNKER OFFLINE

### El límite de `caches.addAll()` en Safari antiguo

`caches.addAll()` es atómico: o cachea todo o no cachea nada. El problema en Safari ≤15 (iOS 15, que es el límite real del A10):

- Safari tiene un límite de Cache Storage **por origen de ~50MB** en dispositivos con poca RAM, expandible hasta ~1GB pero con quotas dinámicas que el sistema puede reducir sin aviso
- `caches.addAll()` con 100 fragmentos HTML + 200 WebPs intenta hacer los 300 fetches y guardarlos en memoria antes de escribirlos a disco
- Si la suma de los recursos supera el límite de RAM disponible para el proceso de Service Worker (que en iOS es un proceso separado con límite propio, típicamente 48MB), Safari mata el SW silenciosamente sin rechazar la promesa — simplemente desaparece
- El resultado: la caché queda en estado inconsistente, parcialmente escrita, y las siguientes visitas fallan de forma no determinista

**El patrón correcto — cachear en lotes secuenciales:**

```javascript
// En el Service Worker
async function cacheInBatches(cacheName, urls, batchSize = 10) {
  const cache = await caches.open(cacheName);
  
  for (let i = 0; i < urls.length; i += batchSize) {
    const batch = urls.slice(i, i + batchSize);
    
    // Cachear cada recurso individualmente para poder manejar fallos parciales
    await Promise.allSettled(
      batch.map(async url => {
        try {
          const response = await fetch(url);
          if (response.ok) await cache.put(url, response);
        } catch (e) {
          console.warn(`Cache miss for ${url}:`, e);
          // Continuar — no bloquear el resto del lote
        }
      })
    );
    
    // Ceder el hilo entre lotes para que iOS no mate el proceso
    await new Promise(r => setTimeout(r, 50));
  }
}
```

### Cache API vs IndexedDB — análisis real

**Cache API: qué hace bien y qué hace mal**

Bien: interceptar requests de red de forma transparente (`fetch` event), almacenar Response objects completos con headers, integración nativa con el ciclo de vida del SW.

Mal: no tiene índices ni queries, no puedes buscar "todos los chunks del Tomo 2", el control de quota es opaco y varía entre navegadores, los datos pueden ser borrados por el sistema operativo en presión de almacenamiento sin notificación al desarrollador (en iOS especialmente, bajo presión térmica o de batería).

**IndexedDB: qué hace bien y qué hace mal**

Bien: quota más generosa y más predecible, transacciones ACID, índices y queries, los datos persisten más agresivamente que Cache API en iOS, puedes almacenar Blobs, ArrayBuffers y strings con control total.

Mal: API asíncrona verbosa (aunque con `idb` wrapper se mitiga), no intercepta requests de red directamente — tienes que coordinarlo con el SW manualmente, mayor complejidad operativa.

**La arquitectura final recomendada — híbrida con responsabilidades separadas:**

```
Cache API                    IndexedDB
─────────────────            ──────────────────────────
Shell HTML (index.html)      Chunks HTML (texto puro)
CSS crítico                  Imágenes grandes (Blobs)
loader.js                    manifest.json
Fuentes web                  Estado de lectura del usuario
                             Metadatos de chunks (altura,
                             posición, timestamp)
```

**El Service Worker actúa de orquestador:**

```javascript
// sw.js
self.addEventListener('fetch', event => {
  const url = new URL(event.request.url);
  
  if (url.pathname.startsWith('/chunks/')) {
    // Los chunks vienen de IndexedDB
    event.respondWith(getChunkFromIDB(url.pathname));
  } else {
    // El resto viene de Cache API
    event.respondWith(
      caches.match(event.request).then(r => r || fetch(event.request))
    );
  }
});

async function getChunkFromIDB(path) {
  const db = await openDB();
  const tx = db.transaction('chunks', 'readonly');
  const html = await tx.objectStore('chunks').get(path);
  
  if (html) {
    return new Response(html, {
      headers: { 'Content-Type': 'text/html; charset=utf-8' }
    });
  }
  
  // Fallback a red si no está en IDB
  const response = await fetch(path);
  // Guardar en IDB para la próxima vez (fuera del critical path)
  storeChunkInIDB(path, await response.clone().text());
  return response;
}
```

## FRENTE 1: Sobre la meta-gobernanza

Esta parte la respondo directamente porque es la más importante para la salud del proyecto.

**El riesgo real no es técnico — es epistémico.** Cuando pasáis el mismo prompt a 10 modelos distintos y recibís 10 respuestas, el "consenso" que emerge no es conocimiento validado. Es la intersección de los datos de entrenamiento de modelos que en muchos casos comparten fuentes. Un error sistemático en esos datos aparece en todas las respuestas y parece consenso.

**El protocolo que realmente previene alucinación colectiva:**

1. **Cada sugerencia de arquitectura debe tener un test empírico antes de construir sobre ella.** No "Grok sugiere virtual scrolling" — sino "probamos virtual scrolling en el iPad A10 real con 50 artículos y medimos FPS y memoria con Safari Web Inspector".

2. **Las instrucciones a los modelos deben incluir el código actual**, no descripciones del código. Los modelos inventan detalles cuando trabajan con descripciones.

3. **Un modelo por ronda, con el output del anterior como input.** No en paralelo — en paralelo amplificáis el ruido. En serie podéis detectar contradicciones.

4. **Ninguna decisión arquitectónica irreversible basada solo en outputs de LLMs.** Los modelos son buenos generando opciones y analizando trade-offs. Malos prediciendo comportamiento de hardware específico sin datos reales.
