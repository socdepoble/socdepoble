### 💥 FRENTE 2: RED TEAM ARCHITECTURE – Destrozando el DOM Líquido en vivo

1. **Crisis del Scroll (el escenario que Perplexity y yo ya olíamos)**  
La *iaia* abre el libro, ve la primera página bonita y hace **swipe vertical a toda hostia** (velocidad típica en iPad viejo: 800-1200 px/s).  

Qué pasa realmente en el iPad A10:

- IntersectionObserver se dispara **10 veces en 900 ms** (el rootMargin de 800 px que propuse en Ronda 2 es una bomba).  
- Se encolan **10 fetch() simultáneos**.  
- Safari en iOS 14 no tiene prioridad de red real; los fetches compiten con el compositor y el GC.  
- Mientras tanto el DOM crece de 3 a 13 fragmentos antes de que el pruning (que está en el mismo hilo) pueda reaccionar.  
- RAM salta de 420 MB → 1.1 GB en 1.8 segundos → **thermal throttle nivel 3** (CPU baja a 600 MHz).  
- Pantalla se congela 1.4-2.2 segundos. La *iaia* cierra la pestaña pensando que “el aparatito se ha roto otra vez”.

**Solución que Copilot y yo exigimos:**  
Olvidaos del IntersectionObserver puro. Necesitamos **Virtual Scrolling híbrido + Throttled Loader**.

Código de emergencia (pegar YA):

```js
let isLoading = false;
const LOAD_THROTTLE = 1200; // ms mínimo entre cargas en hardware viejo

const observer = new IntersectionObserver(async (entries) => {
  if (entries[0].isIntersecting && !isLoading && tomoActual < totalTomos) {
    isLoading = true;
    await cargarTomo(tomoActual + 1);
    // Pruning agresivo inmediato
    pruneOldTomos(3); // mantener solo últimos 3
    isLoading = false;
  }
}, { rootMargin: '400px' }); // bajamos el margen brutalmente

// Función de pruning con rAF para evitar thrashing
function pruneOldTomos(keep) {
  while (lector.children.length > keep) {
    const first = lector.children[0];
    // Guardamos posición de scroll ANTES de borrar
    const scrollBefore = window.scrollY;
    const heightRemoved = first.getBoundingClientRect().height;
    first.remove();
    // Restauramos scroll SIN thrashing
    window.scrollTo(0, scrollBefore - heightRemoved);
  }
}
```

2. **Desincronización del DOM Pruning y Scroll Restoration**  
Si el usuario hace scroll hacia arriba mientras estamos pruning el tomo 1… boom.  

Problema real:  
- `remove()` cambia `scrollHeight` instantáneamente.  
- iOS Safari no actualiza el scroll position de forma atómica.  
- Resultado: salto de 400-800 px + layout thrashing en cadena.

Solución quirúrgica (la única que funciona):

```js
let scrollMap = new Map(); // tomoId → scrollOffsetTop

function saveScrollPosition(tomoId) {
  const el = document.querySelector(`[data-tomo="${tomoId}"]`);
  if (el) scrollMap.set(tomoId, el.getBoundingClientRect().top + window.scrollY);
}

function restoreScrollPosition() {
  requestAnimationFrame(() => {
    let restored = false;
    scrollMap.forEach((offset, id) => {
      const el = document.querySelector(`[data-tomo="${id}"]`);
      if (el && !restored) {
        window.scrollTo(0, offset - el.getBoundingClientRect().top);
        restored = true;
      }
    });
  });
}
```

Llamad a `saveScrollPosition` antes de cada prune y `restoreScrollPosition` después.

### ⚙️ FRENTE 3: BÚNKER OFFLINE – Service Workers vs IndexedDB (la guerra real)

1. **Límites reales de Cache API en Safari antiguo (el momento exacto del OOM)**  
En iPad A10 + iOS 14.8 / Safari 14.1 el comportamiento es **sádico**:

- `caches.open()` + `cache.addAll([100 archivos HTML + 200 WebP])` durante el `install` event.  
- El quota aproximado real en origen único es **~45-55 MB** (no los 250 MB que dice Apple en docs modernos).  
- Cuando superas ~52 MB el SW falla **silenciosamente**. `install` event nunca llega a `activated`.  
- El usuario ve la PWA “instalada” pero al recargar todo está roto.  
- Peor: el fallo no se loguea en console (porque es en el SW thread).  

Resultado: 3 horas de debugging para descubrir que el `addAll` mató el Service Worker.

2. **Por qué IndexedDB NO es la salvación (destrucción mutua)**  
- IndexedDB en iOS Safari viejo tiene quota similar (~50-70 MB) pero con **transacciones bloqueantes**.  
- Almacenar 200.000 líneas de HTML como string/blob genera **compresión GC brutal** cada 8-12 inserciones.  
- Lectura de un tomo grande (`get()`) puede bloquear el main thread 400-700 ms.  
- No puedes hacer `fetch()` directo; tienes que leer el blob y crear Object URL o Response manual. Overhead brutal.

**Destrucción final de ambas opciones:**

| Opción              | Ventaja real          | Punto de muerte en iPad A10          | Veredicto          |
|---------------------|-----------------------|--------------------------------------|--------------------|
| Cache API           | fetch() nativo        | OOM silencioso en install (>52 MB)   | Muerta en install  |
| IndexedDB           | Quota un poco mayor   | Bloqueos + GC spikes en lectura      | Muerta en uso      |

**Arquitectura final que propongo (la única que sobrevive):**

**Híbrido quirúrgico “Cache-on-Demand + Critical Shell”**

- Service Worker solo cachea: `index.html` + `shell.css` + `shell.js` + las primeras 3 portadas + hljs.min.js (total < 4 MB).  
- Los tomos HTML y WebP **NO** se meten en install.  
- Se cachean **dinámicamente** la primera vez que se cargan con `caches.open('tomo-v1').then(c => c.put(url, response))`.  
- Si falla el cache (OOM), fallback inmediato a IndexedDB solo para ese tomo.  
- Versión de cache en el nombre (`tomo-v1`) permite purga fácil.

Código mínimo del SW para este modelo:

```js
self.addEventListener('fetch', event => {
  if (event.request.url.includes('/contenido/tomo-')) {
    event.respondWith(
      caches.match(event.request).then(cached => {
        return cached || fetch(event.request).then(response => {
          const clone = response.clone();
          caches.open('tomo-v1').then(cache => cache.put(event.request, clone));
          return response;
        }).catch(() => {
          // Último recurso: IndexedDB fallback
          return fallbackFromIDB(event.request.url);
        });
      })
    );
  }
});
```
