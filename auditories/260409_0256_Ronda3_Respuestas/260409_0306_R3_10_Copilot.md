#### Simbiosis operativa Asiática vs Occidental
- **Patrón táctico**: Asiáticas proponen agresiva fragmentación y paralelismo; Occidentales imponen límites conservadores y degradación.  
- **Ejemplo táctico**: cuando la capa Asiática sugiere prefetch masivo de N+3 fragmentos, la capa Occidental debe imponer **budgeting**: máximo 2 fetchs concurrentes por usuario y un *prefetch credit* que se consume y regenera lentamente.  
- **Mecanismo**: cada sugerencia de prefetch pasa por un *policy gate* que evalúa `deviceMemory`, `navigator.connection.effectiveType`, `battery` y `userInteractionScore`. Si la suma de riesgos > umbral, se degrada a prefetch bajo demanda.

## RED TEAM ARCHITECTURE Detalles de ataque y análisis destructivo

### FRENTE 1 Crisis del Scroll y Flood de Fetch

**Escenario de ataque**  
Usuario hace un swipe vertical extremo que atraviesa 10 fragmentos en 1 segundo en iPad A10 (2GB RAM). El sistema por defecto: IntersectionObserver detecta entradas, dispara `fetchFragment()` para cada fragmento y `injectFragment()` sin límites.

**Cadena de fallo**
1. **IntersectionObserver** dispara N callbacks casi simultáneos.  
2. Cada callback lanza `fetch` → 10 promesas concurrentes.  
3. iOS WebKit limita conexiones y memoria; múltiples respuestas llegan y se parsean con `innerHTML` → picos de heap.  
4. Garbage collector entra en thrash; CPU sube; thermal throttling reduce clock; UI entra en jank.  
5. Si `highlight.js` se programa inmediatamente, se añade otra carga CPU intensiva → freeze.

**Puntos de ruptura concretos**
- **Número de fetch concurrentes** que iOS tolera antes de matar procesos suele ser bajo; 6–8 fetchs simultáneos con payloads medianos pueden saturar.  
- **Parsing HTML con innerHTML** para fragmentos grandes dispara reflow y consumo de memoria temporal (duplicación de DOM durante parse).  
- **IntersectionObserver** sin debounce ni hysteresis puede generar ráfagas.

**Ataque de prueba**  
- Simular 10 fragmentos de 200KB cada uno; disparar 10 fetchs; medir `JS heap size` y `Long Tasks`. Resultado esperado: OOM o tab crash en dispositivos con 2GB.

**Contramedidas brutales**
- **Semaphore de fetch**: máximo 2 fetchs concurrentes por usuario; cola con prioridad y cancelación por AbortController.  
- **Hysteresis en IntersectionObserver**: sólo disparar prefetch cuando el fragmento está a X px del viewport y el scroll velocity < V.  
- **Budgeting**: cada usuario tiene un *prefetchBudget* regenerable; cada fetch consume crédito.  
- **Progressive streaming parse**: usar `response.body.getReader()` y `DOMParser` incremental para evitar innerHTML completo.  
- **Cancel on overscroll**: si la velocidad de scroll supera umbral, cancelar prefetch en cola.

**Snippet de control de concurrencia y cancelación**
```js
class FetchQueue {
  constructor(concurrency=2){ this.concurrency=concurrency; this.running=0; this.queue=[]; }
  enqueue(task){
    return new Promise((res,rej)=>{
      this.queue.push({task,res,rej});
      this.dequeue();
    });
  }
  dequeue(){
    if(this.running>=this.concurrency) return;
    const item = this.queue.shift();
    if(!item) return;
    this.running++;
    const ctrl = new AbortController();
    item.task(ctrl.signal).then(r=>{ this.running--; item.res(r); this.dequeue(); })
      .catch(e=>{ this.running--; item.rej(e); this.dequeue(); });
  }
}
```

### FRENTE 2 Desincronización del DOM Pruning y Scroll Restoration

**Escenario de fallo**  
Política de pruning: mantener máximo 3 fragmentos en DOM. Usuario scrollea rápido hacia abajo, se prunean fragmentos superiores. Usuario hace scroll brusco hacia arriba; el sistema debe reinyectar fragmentos previos y restaurar scroll sin thrash.

**Problemas concretos**
- **Restauración de scroll** requiere conocer la altura total y offsets de fragmentos no presentes. Si se prunean, el navegador no tiene el layout reservado → reflow masivo cuando se reinyectan.  
- **Race conditions**: reinyectar fragmento A mientras otro fetch cancela o reinyecta B produce saltos de scroll y duplicados.  
- **Scroll anchoring** puede fallar si el contenido anterior cambia tamaño tras la inyección (imágenes sin ratio).

**Ataque de prueba**  
- Prunear fragmentos y eliminar sus placeholders; luego forzar scroll hacia arriba y medir layout thrash y repaint count.

**Contramedidas brutales**
1. **Spacer virtual persistente**: mantener en DOM un *spacer* por cada fragmento pruned con la altura estimada; esto preserva offsets y evita reflow al reinyectar.  
2. **Deterministic height metadata**: manifest incluye `estimatedHeight` por fragmento calculado en build; usarlo para spacers.  
3. **Atomic rehydration**: reinyectar fragmento en un `DocumentFragment` fuera del DOM, medir su altura, then replace spacer in a single `requestAnimationFrame` to avoid intermediate layouts.  
4. **Optimistic prefetch on reverse scroll**: si user velocity indicates reverse intent, prefetch previous fragment with high priority.  
5. **Locking**: usar un simple mutex por slot para evitar reentrancy en rehydration.

**Snippet de rehydration seguro**
```js
async function rehydrateFragment(id, spacerEl){
  const html = await fetchQueue.enqueue(signal => fetchFragment(id, {signal}));
  const df = document.createRange().createContextualFragment(html);
  // measure off-DOM
  const temp = document.createElement('div'); temp.style.position='absolute'; temp.style.visibility='hidden';
  temp.appendChild(df.cloneNode(true));
  document.body.appendChild(temp);
  const measured = temp.offsetHeight;
  document.body.removeChild(temp);
  // replace spacer atomically
  requestAnimationFrame(()=>{
    const frag = document.createElement('div'); frag.className='fragment'; frag.innerHTML = html;
    spacerEl.replaceWith(frag);
  });
}
```

### FRENTE 3 Service Workers Cache API y IndexedDB

#### Limitaciones y fallos de Cache Storage
- **`caches.addAll()`** intenta abrir múltiples requests y almacenar respuestas completas en memoria temporal antes de escribir en storage. En navegadores antiguos o con implementaciones pobres (versiones antiguas de Safari iOS), esto puede consumir memoria lineal con el tamaño total de los recursos y provocar OOM.  
- **Límite de quota**: algunos WebKit devs aplican límites estrictos por origen; intentar cachear 100 fragmentos y 200 imágenes de golpe puede exceder quota y fallar la operación sin excepción clara.  
- **Eviction policy**: Cache Storage no garantiza LRU; el navegador puede purgar sin aviso cuando la cuota se supera.

**Ataque de prueba**
- En el SW `install` llamar `caches.addAll([...100 fragments, 200 images])` y observar crash o fallos silenciosos en `install` que dejan la PWA sin recursos.

#### Por qué IndexedDB es preferible para blobs masivos
- **Escritura incremental**: IndexedDB permite transacciones y escritura por chunks; no requiere mantener todo en memoria antes de persistir.  
- **Control de chunking y compresión**: podemos escribir blobs en trozos y aplicar compresión incremental.  
- **Metadatos y LRU**: podemos implementar un índice LRU y políticas de purga explícitas.  
- **Atomicidad**: transacciones permiten rollback parcial.

**Ataques contra IndexedDB**
- Escrituras masivas sin chunking pueden bloquear el event loop por largos periodos en implementaciones antiguas.  
- QuotaExceededError si se intenta almacenar más de lo permitido; manejo incorrecto puede dejar datos en estado inconsistente.

#### Arquitectura final recomendada (endurecida)
- **Hybrid store**:  
  - **Cache Storage** para shell, CSS, JS y fragments pequeños y críticos (N pequeño).  
  - **IndexedDB** para fragments grandes y blobs de imágenes pesadas.  
- **Write strategy**: stream download → chunk → write to IndexedDB → create object URL para servir. No usar `caches.addAll` para lotes grandes.  
- **Eviction**: LRU index en IndexedDB con `lastAccessed` timestamp; background cleanup cuando `usedQuota` > threshold.  
- **Install strategy**: cache minimal shell only; lazy populate rest on first use with background sync and throttled writes.  
- **Quota awareness**: detectar `navigator.storage.estimate()` y adaptar prefetch budget.

**Snippet de escritura chunked a IndexedDB**
```js
async function storeStreamToIDB(stream, key){
  const db = await openIDB();
  const tx = db.transaction('blobs','readwrite');
  const store = tx.objectStore('blobs');
  const reader = stream.getReader();
  let chunks = [];
  while(true){
    const {done,value} = await reader.read();
    if(done) break;
    chunks.push(value);
    if(chunks.length >= 8){ // flush every 8 chunks
      const blob = new Blob(chunks);
      await store.put({key, blob, ts:Date.now()});
      chunks = [];
    }
  }
  if(chunks.length) await store.put({key, blob:new Blob(chunks), ts:Date.now()});
  await tx.complete;
}
```

## Lista exhaustiva de fallos y recomendaciones concretas

#### 1. IntersectionObserver flood
- **Fallo**: callbacks sin debounce.  
- **Recomendación**: add hysteresis, velocity gating, and prefetchBudget.

#### 2. Fetch concurrency
- **Fallo**: demasiadas promesas concurrentes.  
- **Recomendación**: semaphore con AbortController y priority queue.

#### 3. innerHTML parsing
- **Fallo**: parsea HTML grande en main thread.  
- **Recomendación**: stream parse con `response.body` y `DOMParser` incremental; parse off-DOM.

#### 4. Highlighting
- **Fallo**: highlightAll en main thread.  
- **Recomendación**: WebWorker highlight pipeline that returns sanitized HTML; fallback to idle-chunking.

#### 5. Images and CLS
- **Fallo**: images without reserved space.  
- **Recomendación**: manifest includes width/height; use aspect-ratio placeholders; decode async.

#### 6. Pruning race conditions
- **Fallo**: concurrent prune + rehydrate.  
- **Recomendación**: per-slot mutex, atomic replace via requestAnimationFrame, persistent spacers.

#### 7. Cache Storage OOM
- **Fallo**: caches.addAll massivo.  
- **Recomendación**: incremental caching, stream-to-IDB for large assets, avoid addAll for >N items.

#### 8. IndexedDB write blocking
- **Fallo**: writes block event loop.  
- **Recomendación**: chunked writes, yield to event loop, use setTimeout 0 or postMessage to break long tasks.

## Política de degradación y heurísticas de detección

**Detectores y thresholds**
- **deviceMemory**: if ≤ 2 → *lowMemoryMode*  
- **hardwareConcurrency**: if ≤ 2 → reduce parallelism  
- **navigator.connection.effectiveType**: if `2g|slow-2g` → disable prefetch  
- **battery.level**: if < 0.2 → aggressive pruning  
- **scrollVelocity**: if > Vfast → suspend prefetch and cancel queued fetches

**Degradación progresiva**
1. **Normal**: concurrency 2, prefetch N+1, highlight worker enabled.  
2. **Constrained**: concurrency 1, prefetch disabled, highlight idle-chunking.  
3. **Critical**: only current fragment in DOM, images placeholders only, code highlighting deferred until user taps.
