### 1. Política de desalojo de IndexedDB en Safari — el vector más peligroso

Safari en iOS usa **Jetsam** para gestión de memoria y un sistema de cuotas de almacenamiento que no se comporta como la especificación W3C promete.

El problema concreto: Safari clasifica el almacenamiento de PWAs instaladas en la pantalla de inicio como "persistent" pero **lo trata como "best-effort"** en la práctica. En iOS 14, si el sistema necesita espacio, puede vaciar el almacenamiento de una PWA sin notificación, sin llamar a ningún evento, sin posibilidad de interceptarlo. El límite documentado es 50MB por origen en modo navegador; en modo PWA instalada es potencialmente mayor, pero no está garantizado.

Lo que falta en la arquitectura actual: no hay detección de desalojo ni recuperación.

```javascript
// idb-guardian.js — detectar desalojo y recuperar estado
class IDBGuardian {
  #SENTINEL_KEY = 'sdp_integrity_sentinel';
  #SENTINEL_VALUE = 'v1_intact';
  
  async verifyIntegrity() {
    const db = await openDB();
    const tx = db.transaction('meta', 'readonly');
    const sentinel = await tx.objectStore('meta').get(this.#SENTINEL_KEY);
    
    if (sentinel !== this.#SENTINEL_VALUE) {
      // IDB fue vaciada — lanzar recuperación
      console.error('[IDB] Desalojo detectado. Iniciando recuperación.');
      await this.#recover();
      return false;
    }
    return true;
  }

  async #recover() {
    // 1. Notificar al usuario con UI no bloqueante
    this.#showRecoveryBanner();
    
    // 2. Re-cachear chunks en orden de prioridad (los primeros primero)
    const manifest = await fetch('./chunks/manifest.json').then(r => r.json());
    const queue = new ChunkQueue();
    
    // Solo precachear los primeros 5 chunks — el resto bajo demanda
    for (const entry of manifest.slice(0, 5)) {
      queue.enqueue(entry);
    }
  }

  async writeSentinel() {
    const db = await openDB();
    const tx = db.transaction('meta', 'readwrite');
    await tx.objectStore('meta').put(this.#SENTINEL_VALUE, this.#SENTINEL_KEY);
  }

  #showRecoveryBanner() {
    const banner = document.createElement('div');
    banner.style.cssText = `
      position: fixed; bottom: 0; left: 0; right: 0; z-index: 9999;
      background: #92400e; color: white; padding: 12px 16px;
      font-size: 15px; text-align: center;
    `;
    banner.textContent = 'Reconstruint la biblioteca local... Un moment.';
    document.body.appendChild(banner);
    
    // Eliminar cuando la recuperación termine
    window.addEventListener('sdp:recovery-complete', () => banner.remove(), { once: true });
  }
}

// Ejecutar en cada inicio de la PWA
const guardian = new IDBGuardian();
await guardian.verifyIntegrity();
await guardian.writeSentinel(); // renovar sentinel tras verificación
```

### 2. Corrupción silenciosa del Service Worker

El SW puede quedar en estado zombie: instalado, activado, pero con una versión del `manifest.json` cacheado que no coincide con los chunks actuales. Esto ocurre cuando actualizáis los chunks sin incrementar la versión del SW.

```javascript
// sw.js — sistema de versiones con verificación de integridad
const SW_VERSION = 'sdp-v1.4.2'; // incrementar en cada deploy
const CACHE_SHELL = `shell-${SW_VERSION}`;
const MANIFEST_HASH_KEY = 'sdp_manifest_hash';

self.addEventListener('activate', event => {
  event.waitUntil(async function() {
    // Eliminar caches de versiones anteriores
    const keys = await caches.keys();
    await Promise.all(
      keys
        .filter(k => k.startsWith('shell-') && k !== CACHE_SHELL)
        .map(k => caches.delete(k))
    );

    // Verificar que el manifest en cache coincide con el actual
    await verifyManifestIntegrity();
  }());
});

async function verifyManifestIntegrity() {
  const response = await fetch('./chunks/manifest.json', { cache: 'no-store' });
  const manifest = await response.json();
  const hash = await computeHash(JSON.stringify(manifest));
  
  const stored = await idbGet('meta', MANIFEST_HASH_KEY);
  if (stored && stored !== hash) {
    console.warn('[SW] Manifest cambió — invalidando chunks cacheados');
    const db = await openDB();
    const tx = db.transaction('chunks', 'readwrite');
    await tx.objectStore('chunks').clear();
    // No borrar 'meta' — mantener posición de lectura del usuario
  }
  
  await idbPut('meta', MANIFEST_HASH_KEY, hash);
}

async function computeHash(str) {
  const buffer = new TextEncoder().encode(str);
  const hashBuffer = await crypto.subtle.digest('SHA-256', buffer);
  return Array.from(new Uint8Array(hashBuffer))
    .map(b => b.toString(16).padStart(2, '0'))
    .join('').slice(0, 16); // 16 chars suficientes para este caso
}
```

### 3. Persistencia de posición de lectura — el vector humano más crítico

Ninguna ronda anterior ha tocado esto. Si la PWA se recarga (por Jetsam, por actualización, por el usuario), la iaia pierde su posición en un documento de 200.000 líneas. Este es el fallo de UX más grave posible para el caso de uso real.

```javascript
// reading-position.js
class ReadingPosition {
  #STORE = 'meta';
  #KEY = 'sdp_reading_position';
  #saveDebounceTimer = null;

  async save(articleIndex, scrollOffset) {
    // Debounce — no escribir a IDB en cada frame de scroll
    clearTimeout(this.#saveDebounceTimer);
    this.#saveDebounceTimer = setTimeout(async () => {
      await idbPut(this.#STORE, this.#KEY, {
        articleIndex,
        scrollOffset,
        timestamp: Date.now()
      });
    }, 500);
  }

  async restore() {
    const position = await idbGet(this.#STORE, this.#KEY);
    if (!position) return null;
    
    // Si la posición tiene más de 30 días, ignorar
    if (Date.now() - position.timestamp > 30 * 24 * 60 * 60 * 1000) {
      return null;
    }
    return position;
  }
}

// Integrar en VirtualScroller
// En el constructor, tras inicializar:
const savedPos = await readingPosition.restore();
if (savedPos) {
  this.#viewport.scrollTop = this.#heightMap.offsetOf(savedPos.articleIndex) + savedPos.scrollOffset;
  // Mostrar toast no intrusivo
  showToast(`Reprenent la lectura des del capítol ${savedPos.articleIndex + 1}`);
}

// En el handler de scroll del VirtualScroller:
readingPosition.save(centerIndex, scrollY - this.#heightMap.offsetOf(centerIndex));
```

### 4. El problema de `contain: layout style` en Safari 14

La propiedad `contain: strict` que usé en la Ronda 4 para los nodos del pool tiene un bug conocido en Safari 14: puede causar que el contenido desborde visualmente fuera del nodo en ciertos casos con imágenes de altura variable. El valor seguro para este target es:

```javascript
// ANTES (Ronda 4 — potencialmente problemático en Safari 14)
node.style.cssText = `
  position: absolute; left: 0; width: 100%;
  will-change: transform;
  contain: layout style;
`;

// AHORA — más conservador, mismo beneficio en A10
node.style.cssText = `
  position: absolute; left: 0; width: 100%;
  will-change: transform;
  contain: layout;
`;
// 'contain: style' puede causar problemas con contadores CSS y algunos
// selectores en Safari. 'contain: layout' solo es seguro y suficiente
// para evitar que el layout del nodo afecte al resto del documento.
```

### 5. Eficiencia energética — lo que nadie ha mencionado

El `will-change: transform` en los 3 nodos del pool promociona cada nodo a su propia capa GPU. En el A10, esto consume memoria de GPU (que comparte pool con la RAM principal). Con 3 nodos activos más el compositor del navegador, podéis estar usando 30–50MB adicionales de VRAM para las texturas. Para un documento principalmente textual, esto es un mal trato.

```javascript
// Solo activar will-change durante el scroll activo
let scrolling = false;
let scrollEndTimer = null;

viewport.addEventListener('scroll', () => {
  if (!scrolling) {
    scrolling = true;
    pool.forEach(node => node.style.willChange = 'transform');
  }
  
  clearTimeout(scrollEndTimer);
  scrollEndTimer = setTimeout(() => {
    scrolling = false;
    // Liberar capas GPU cuando el scroll para
    pool.forEach(node => node.style.willChange = 'auto');
  }, 150);
}, { passive: true });
```
